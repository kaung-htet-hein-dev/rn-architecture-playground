Across the Bridge

You write React Native every day. Let’s slow it down and look at what happens underneath: first in the old architecture, then in the New Architecture that replaced it. Seven short chapters, then a playground where you can poke at everything.

Old architecture New Architecture JS thread Shadow thread UI thread
CHAPTER 01

One tap, slowed down

WHY

You press buttons all day. If we slow one press down, you’ll see every place where an app can lose time. That becomes our map for the rest of the course.

WHAT

A tap starts on the native side, the iOS or Android code the phone runs for its own UI. It travels to your JavaScript, and your answer travels back. Each side works on its own thread: a single line of work that does one thing at a time, in order.

HOW

The UI thread draws the screen and receives touches. The JS thread runs your React code. In the old architecture they talk through the bridge, which only carries text. So every message is serialized, turned into a JSON string, and parsed back on the other side.

The UI thread draws the screen and receives touches. The JS thread runs your React code. In the New Architecture there is no bridge: JS and C++ call each other through JSI, and data stays as real values, so nothing is turned into text. Work still waits its turn on the right thread.

Flip Old / New in the top bar to replay this exact tap in the other architecture.

CHAPTER 02

The old map

WHY

When something feels slow, the first question to ask is: which thread is busy? You can only answer that if you know which threads exist and what each one does.

WHAT

Three threads. The JS thread runs React. The Shadow thread works out layout, meaning where each box goes and how big it is, using a library called Yoga. The UI thread creates the real views and handles touches.

HOW

The bridge connects JS to the native threads, and everything on it is asynchronous: you send a message and carry on, and the answer arrives later. Messages are queued and sent in batches, groups sent together to save work. Neither side can reach over and read the other’s data.

You’re looking at the New Architecture version of the map. The same three threads exist. What changed is the connection: the bridge is replaced by JSI, and the shadow tree moves into C++ where every thread can read it. Switch back to Old to see the original.
CHAPTER 03

Where it hurt

WHY

Smooth scrolling means a new picture every 16.6 ms, which is 60 pictures per second. Each picture is a frame. When the app misses that window, the user sees a stutter: a dropped frame.

WHAT

Both phones scroll the same list. The scrolling itself is native, but every scroll event asks JS to render more rows. When JS falls behind, you get blank rows. Drag the load slider to make each event’s JS work heavier.

HOW

Both phones merge scroll events that pile up while JS is busy. The difference is the cost: on the old phone every event pays for JSON twice, the scroll event coming in and the row updates going out. The further JS falls behind, the more rows it has to send, so each bridge batch gets bigger and slower. The new phone skips the JSON. Heavy JS is still heavy, though: push the slider to the end.

CHAPTER 04

JSI: holding a reference instead of sending a message

WHY

You call native modules all the time: code written in Swift, Kotlin or Java that JS can use, like reading the battery level. On the bridge, even a tiny question becomes a round trip of messages.

WHAT

JSI, the JavaScript Interface, lets JS hold a reference to an object that lives in C++, a fast, lower-level language that runs on both iOS and Android. That object is a host object: to JS it looks normal, but its methods are C++ functions.

HOW

Instead of writing a letter and waiting for a reply, JS just calls the function. No JSON, no queue, no lookup table. If the method is synchronous, the value comes back on the same line. Toggle Old / New to compare the two trips.

CHAPTER 05

Turbo Modules and Codegen

WHY

Users judge your app in its first second. In the old architecture, most native modules in your app are created at launch by default, even the ones the first screen never touches.

WHAT

A Turbo Module is a native module built on JSI that loads lazily: the first time JS asks for it, not before. Codegen is a build-time tool that reads a TypeScript description of the module and writes the matching native code.

HOW

First, play both startups and compare when the first screen becomes usable. Then step through Codegen turning a spec into a typed C++ interface, so a mismatch between JS and native fails the build instead of crashing on a user’s phone.

CHAPTER 06

Fabric: render, commit, mount

WHY

Every setState you call ends up as real views on screen. The part that turns React’s output into those views is the renderer. Fabric is the New Architecture’s renderer.

WHAT

It works in three phases. Render: React runs your components and Fabric builds a shadow tree, a C++ copy of your UI. Commit: layout is calculated and the tree is sealed. Mount: the changes are applied to host views, the real platform views.

HOW

Because the shadow tree lives in C++ and is shared through JSI, any thread can read it. That is what lets you measure layout synchronously, and lets React render urgent updates first. Step through the three phases and watch the three trees fill in.

You’re seeing the old renderer first, so you have something to compare against. The same three phases happened, but spread over three threads and stitched together with JSON. Step through it, then flip to New to watch Fabric do the same work.

Migration notes

  1. 01Upgrade to a current React Native version. The New Architecture is on by default from 0.76.
  2. 02Check your libraries first. The interop layer lets many old-style modules and components run unchanged while their authors catch up.
  3. 03Move your own native modules to Turbo Modules: write a TypeScript spec, run Codegen, implement the generated interface.
  4. 04Search for code built around the bridge: setNativeProps, findNodeHandle, direct UIManager calls. Test those screens closely.
  5. 05Profile again after migrating. JSI removes serialization overhead, not slow JavaScript.
